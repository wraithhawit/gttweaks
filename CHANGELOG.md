# Version history

This repository begins with the existing 0.25.0 source snapshot. Earlier development happened locally; the entries below summarize the immediately preceding changes and do not imply reconstructed Git history.

## 0.30.0

First Refined Storage multiblock parts. GregTech's ME parts let an AE2 network feed a multiblock; this is the same idea against a Refined Storage network, and the intent is all eight parts. All eight are written, registered and evidenced end to end: an autocrafting request publishes a pattern, the sink delivers its ingredients into a buffer slot, a multiblock runs from that slot, and the products return to the network. The four parts that need configuring now have a screen to do it in, which is what turns them from working into usable; it has since been used in a client, with the gaps listed at the end of this entry. The output bus, pattern buffer and proxy got screens of their own on 2026-09-23. See [docs/RS-PARTS.md](docs/RS-PARTS.md) for the design and what is still missing.

- New machine `gttweaks:rs_input_bus` (RS Input Bus, EV, `IMPORT_ITEMS`): sixteen slots, each a configured resource and amount, kept stocked from a Refined Storage network and handed back when the configuration changes. The multiblock reads those slots as it would an ordinary input bus, so nothing in GregTech's recipe handling knows a network is involved. This is `MEInputBusPartMachine` re-expressed over `StorageNetworkComponent.insert/extract`, with `ExportOnlyAESlot`'s config/stock pair re-expressed over Refined Storage's `ResourceAmount` (`RSConfiguredSlot`, `RSConfiguredItemSlot`, `RSConfiguredItemList`). Registration goes through a `GTRegistrate` of this mod's own, declared to GregTech by `@GTAddon("gttweaks")`; the model points at GregTech's AE2 overlay texture as a placeholder, so the part currently looks like an ME part.
- Two departures from the ME bus, both deliberate. It does not void: when the network refuses the excess a slot is handing back, the ME bus deletes it to free the slot, and this one keeps it and retries. And `ResourceAmount` rejects a non-positive amount where AE2's `GenericStack` allows zero, so the "already stocked, nothing to do" cases return null instead of a zero-sized request.
- Two load-order facts, each found by a server that would not start. Building a machine calls `MachineBuilder.colorOverlayTieredHullModel`, which class-loads `GTMachineModels`, whose static initialiser reads GregTech's casings: from the mod constructor and from `IGTAddon.gtInitComplete()` alike that throws `NullPointerException: null key in entry: null=gtceu:block/casings/solid/machine_casing_bronze_plated_bricks` during mod construction. GregTech builds its own machines inside its `RegisterEvent` handler, right after `GTBlocks.init()`, so `RSMachines.initOnce()` runs on the first registry dispatch too — from a listener added before the registrate's own, so the parts exist when the registrate looks for them. `ordering="AFTER"` on the gtceu dependency does not help; it orders event dispatch, not this.
- Refined Storage finds the part through a block capability (`RSCapabilities`), not by scanning: without that registration the node exists, holds its container and is on no network, silently. Leaving the network happens only in `onMachineUnload`, which covers a broken block too because `MetaMachine.setRemoved()` is final and calls `onUnload()`. Doing it in `onMachineDestroyed` as well threw `IllegalArgumentException: The removed container should be present in the removed entries, but isn't` out of breaking the block. The order is the opposite of what the names suggest — `MetaMachineBlock.onRemove` calls `onMachineDestroyed()` and only then `level.removeBlockEntity(pos)`, so the destroy hook runs first and the throw came from the first removal attempt, not a duplicate of the second. Why Refined Storage accepts the removal from `onUnload` and not from `onMachineDestroyed` is not established; the block state at that position is already replaced at both points. `RSNodeHolder.left` stops a second attempt regardless, since a queued removal leaves `node.getNetwork()` set for another tick.
- Verified on the test server (0.30.0, md5 53c1d9ed), against a creative controller, a cable, and an external storage reading a chest: the part registers as block and item; joins the network and reports `online`, node `active`; stocked 16 cobblestone and 8 iron ingots from configured slots, and the chest behind the external storage went 64 to 48 and 32 to 24; clearing a slot's configuration returned its 16 cobblestone to the chest; configuration and stock survived a full server restart and the part rejoined by itself; and breaking the block returned its 20 cobblestone to the network with no exception. New `/gttweaks rspart <pos> [config <slot> <item> <amount>|config <slot> clear]` is what made those checks possible without a client, and stands in for the slot UI until it exists.
- Not done as of the input bus, and tracked to their own entries below: the output bus, the fluid hatches and the stocking variants all landed later in this version. Still not done at all: the configuration UI (the slots of every input part can only be set by command, which is what keeps them out of normal play), the pattern buffer and its proxy, crafting recipes, and textures of their own. Nothing in this version has been run in a client or driven by an actual multiblock recipe.
- Astra review of 0.30.0 (consult log `20260918-170840.md`), two confirmed defects and a design point, all acted on. Item conservation was broken in `returnExcess` and the destroy flush: the network was credited a `long` and the slot debited an `int` through `extractItem`, so an insert above `Integer.MAX_VALUE` left items behind that the network had also received, and a non-item resource in the slot was inserted repeatedly while `extractItem`'s `instanceof ItemResource` guard refused to debit it at all. Both amounts are reachable: the slot setters and the NBT path place no integer bound on a configured amount. `RSConfiguredSlot.debitStock(long)` now removes exactly what the network accepted, in the resource's own units, and neither accounting path touches the item handler. `RSConfiguredItemSlot.setConfig` refuses a non-item resource, while stock is left unpoliced on purpose — a slot holding one now empties itself back to the network instead of needing anything discarded.
- The deferred join could outlive the machine. `onMachineLoad` schedules the join a tick later and the server, not the machine, holds that task, so a part broken or unloaded inside that one-tick window would still build a container, hand it to Refined Storage, and leave it on the network with nothing behind it — and `leave()` had already run and found no network to leave, so nothing would take it off again. `RSNodeHolder.unloaded` is set by `onMachineUnload` and checked by the join, along with `isRemoved()`. Not exercised by a test; the window is one tick.
- `RSCapabilities` asked the block entity to be an `RSBusPartMachine`. The fluid hatches will extend GregTech's fluid part class, so that cast would have compiled and thrown the first time a cable touched a hatch; parts now answer through a new `RSNetworkPart` interface.
- Returning a broken part's stock to the network, rather than dropping it, is the intended behaviour and stays: a slot's amount is a `long` and a bus can hold hundreds of thousands of items, so `modifyDrops` would trade a rare loss for an entity flood. The remaining gap is only the offline-or-full case, where the stock is still lost with the block; carrying it on the dropped machine item through `collectImplicitComponents` is the likely answer. Astra's converse worry is settled and is not a risk: GregTech never drops a bus's contents, so this flush cannot double up with a drop — `MetaMachine.modifyDrops` is empty, neither `ItemBusPartMachine` nor `TieredIOPartMachine` overrides it, and `MetaMachineBlock.onRemove` only calls `onMachineDestroyed` and removes the block entity.
- Also raised and deliberately kept: not voiding excess can leave a slot stuck rather than merely stalled — a bus holding A, reconfigured to B, against storage full of B needs space to return A and would make space by extracting B, which it refuses to do while A is held. A resource dependency cycle, not a hang, and keeping a player's items is still the better failure. Untested: an actual multiblock recipe drawing from the slots, and whether GregTech drops a bus inventory on break in addition to this flush, which would duplicate.
- Re-verified after the fixes (md5 a135f064): stocked 25 cobblestone from a 64-stack chest (39 left), dropping the configured amount to 10 returned exactly 15 (54), breaking the part returned exactly 10 (64) — every item accounted for across the whole sequence — and no `removed entries` error or gttweaks frame in the log.

- Three more parts, all verified: `gttweaks:rs_output_bus` (RS Output Bus, EV, `EXPORT_ITEMS`), `gttweaks:rs_input_hatch` (RS Input Hatch, EV, `IMPORT_FLUIDS`) and `gttweaks:rs_output_hatch` (RS Output Hatch, EV, `EXPORT_FLUIDS`). The output parts have no configuration — whatever the multiblock leaves in them goes to the network — so they are driven in testing by writing into the inventory or tank a multiblock would have filled, and the live trait reads that back rather than merely storing it.
- The fluid side is the item side's shape, bent around two facts about GregTech's classes. `RSConfiguredSlot` turned out to be resource-agnostic already — it holds a `ResourceAmount` and never asks what kind — so the fluid slots reuse it unchanged; but `CustomFluidTank` is a *class* where `IItemHandlerModifiable` is an interface, so `RSConfiguredFluidSlot` cannot extend both it and `RSConfiguredSlot` and holds the configured slot as a private inner class instead. That asymmetry is the only reason the two sides do not read identically. `CustomFluidTank` also brings its own `INBTSerializable`, which would have written the superclass's permanently-empty tank over the real stock and wiped the part on every reload; `RSConfiguredFluidSlot` overrides `serializeNBT`/`deserializeNBT` to persist the configured slot instead. And Refined Storage gives `ItemResource` an `ofItemStack`/`toItemStack` pair but gives `FluidResource` neither, so `RSFluids` is that missing pair — going back to a `FluidStack` needs `BuiltInRegistries.FLUID.wrapAsHolder(...)`, since `Fluid.builtInRegistryHolder()` is deprecated.
- Verified on the test server 2026-09-20 (0.30.0, md5 1aa035ec), with exact counts on both sides of each move: the input bus took 32 cobblestone from a 64-stack and left 32, the output bus handed over 17 diamonds and 5 gold ingots and emptied itself, the output hatch pushed 16000 mB of water into the network, and the input hatch pulled back exactly its configured 5000. Each of the four registers, joins a network through the capability, moves what it should in the direction it should, keeps its configuration and stock across a full server restart, and rejoins by itself afterwards. One trap worth recording for anyone testing the fluid half: **a network with no fluid storage silently refuses every fluid insert**, which looks exactly like a broken output hatch — `refinedstorage:creative_fluid_storage_block` in the test rig is what makes the fluid side testable at all.
- Two stocking parts, `gttweaks:rs_stocking_bus` and `gttweaks:rs_stocking_hatch`, both verified. They are a window onto the network rather than a buffer: the configured *amount* is ignored and the slot reports whatever the network holds.
- `MIRROR_REQUEST` (`Integer.MAX_VALUE`) is what both stocking parts ask the network for, not `Long.MAX_VALUE` as GregTech's mirror asks AE2. Refined Storage cannot answer the larger question on either side, and both failures are a narrowing cast rather than a clamp: `ItemHandlerExtractableStorage.extract` computes the amount still wanted as a `long` and passes it to `extractSlot` as `(int) toExtract`, so `Long.MAX_VALUE` arrives as `-1`, `extractItem(slot, -1, ...)` yields nothing and every slot is skipped — a chest behind an external storage would mirror as permanently empty. `VariantUtil.toFluidStack` looks safer and is not: it logs `Truncating too large amount ...` and then builds the `FluidStack` with `(int) amount` anyway, reaching the same `-1`. Both read off Refined Storage 2.0.9's own sources, not inferred. The cost is a mirror that cannot display more than about 2.1 billion of one resource, which no caller could draw in one go regardless, since `extractItem` and `drain` both take an `int`. Written from those sources before either part had ever been run. The mirrors do now report true amounts with it in place, but the pre-fix build was never run against this rig, so the empty-mirror failure it fixes remains a reading of Refined Storage's code rather than something observed here.
- New `/gttweaks rspart <pos> extract <slot> <amount> <simulate>`, which drives the one path a multiblock drives and exists because the `simulate` flag cannot be reached any other way. GregTech runs a simulated recipe pass before a real one, so a stocking slot that ignored the flag would consume the inputs of every recipe it merely *considered*, and the network would drain with nothing to show for it — invisible in game until the storage is gone. Nothing a player or a hopper can do asks for a simulated extraction. The command goes through the slot's own `extractItem`/`drain` rather than through the part, because that is the method GregTech's recipe logic calls and the one a stocking slot overrides to reach the network. Written for the stocking checks below, and used to run them.
- Verified the two stocking parts on the test server 2026-09-21 (0.30.0, md5 cfa642075b6a63619ce0ca7f01f401ee), the first time either had been run at all. Both joined the network and went active the moment they were placed. The bus, against a 64-stack of cobblestone in the chest behind the external storage: configured `1 x cobblestone`, it mirrored **64** and left the chest at 64, so the configured amount is ignored and the network's own total is reported without drawing on it; a simulated extract of 16 reported 16 and moved nothing (chest 64, mirror 64); a real extract of 16 reported 16 and took the chest to 48 with the mirror re-reading 48, so it debits exactly once; and breaking the block while it mirrored 48 left the chest at 48, which is the duplication case that matters most for a mirror.
- The hatch was checked the same way, using the already-verified input hatch as a measuring cup: configure it for more water than exists and it pulls the network dry, so its stock is an independent readout of the network total that runs no stocking code. (RS keeps storage contents in its own saved data rather than the block entity, so `/data get block` on a fluid storage block returns only a storage id and cannot serve as that readout; and the creative fluid storage block has infinite capacity, not infinite contents, so the total is finite and knowable.) Network water measured 16000 mB, matching what the output hatch pushed on 2026-09-20. The mirror read 16000 against its configured 1; a simulated drain of 1000 reported 1000 and left it at 16000; a real drain of 1000 took it to 15000 and an independent re-measure returned **exactly 15000**, so the simulation consumed nothing and the real drain debited once. Draining the network out from under the mirror dropped it to empty and returning the water restored it to 15000, so it tracks down as well as up. Breaking it while it mirrored 15000 left the network at 15000. Across the whole run: 0 `ERROR` lines after startup, no `removed entries` exception, no gttweaks stack frame.
- One testing gotcha worth recording: a slot is filled from the part's own tick, not from the command that configured it, so an `rspart` query issued immediately after a `config` reports `stock -` and has to be repeated. That empty first reading is not a failure.
- Restart check for the stocking pair, same day: configured with deliberately odd amounts (`7 x cobblestone`, `3 mB water`, small enough that neither could be confused with a default or with the amount being mirrored), the server stopped and started. Both came back with those configurations intact, rejoined the network and went active by themselves, and the mirrors were shown to be live rather than restored-stale — replacing the chest's stack with 20 cobblestone moved the bus's mirror from 48 to 20. 0 `ERROR` lines after startup. One transient to expect: queried about three seconds after `Done`, the bus reported `online: false`, `active: false` and `network storage: unreachable` while still showing `joined`; ten seconds later it was fully online with no intervention. The network takes a moment to initialise and power after a world load, and a part queried inside that window looks broken when it is not.
- New machine `gttweaks:rs_pattern_buffer` (RS Pattern Buffer, EV, `IMPORT_ITEMS` + `IMPORT_FLUIDS`), the seventh of the eight parts. It holds encoded Refined Storage patterns, publishes them to the network's autocrafting through a `PatternProviderNetworkNode`, and receives a task's ingredients into its own internal slots for the multiblock to consume. Every piece of that is public, `@API(STABLE)` Refined Storage: the node is concrete and extends `SimpleNetworkNode`, `RefinedStorageApi.getPattern` turns a pattern item into a `Pattern`, `PatternProviderItem.isValid` filters the pattern inventory, and `node.setSink(...)` takes a sink of ours whose `accept(Collection<ResourceAmount>, Action)` is where the ingredients land. The RS half is easier than AE2's, which hands over a `KeyCounter[]` and expects the callee to drive `pushInputsToExternalInventory`; RS hands over the `ResourceAmount`s directly, already the shape a slot wants.
- Each slot is offered to the recipe logic as its **own** set of inputs, not as part of a pool, which is the whole point of the part: pooling would let one recipe take half its inputs from one pattern and half from another and complete neither. `RSBufferRecipeHandlerList` enforces it by walking the slots and asking whether each could satisfy the *entire* remaining recipe alone — running the full consume pass in simulation and checking nothing is left over — and only then letting that slot run it for real. A slot that could satisfy most of a recipe is no use and is skipped. The per-slot handlers consume when asked; the aggregate handlers report contents and deliberately consume nothing, existing only so the multiblock believes the part offers item and fluid inputs at all.
- Verified on the test server 2026-09-21 (0.30.0, md5 555fc41c): the part registers as block and item, places, joins a network through the capability and reports `active: true`; a slot took 11 diamonds and 1234 mB of water together and reported both; those contents survived a full server stop and start unchanged; and breaking the part while it held them gave the network back exactly 11 diamonds (chest 17 → 28) and exactly 1234 mB (network water 15000 → 16234, measured with the input hatch as a measuring cup). 0 `ERROR` lines after startup, no `removed entries`, no gttweaks frame.
- **Not verified, and the part is not usable yet:** no real encoded pattern has ever reached it, so the pattern publishing and the sink's own `accept` are untested, and no multiblock has drawn from a slot, so the distinct matching above is unexercised. An encoded pattern cannot be made headlessly — it needs a player at a Pattern Grid. The new `/gttweaks rspart <pos> buffer <slot> item|fluid …` reaches the same `RSBufferSlot` the sink fills and is what the checks above used; it stands in for a task, it is not one.
- A save-system trap, found by a restart rather than by the compiler. `@SaveField` on a `List<RSBufferSlot>` restored as **empty**, so the part came back from a restart with no slots and refused every delivery with "this part has 0". An array of `INBTSerializable` round-trips through GregTech's save system; a `List` of them silently does not. GregTech's own buffer persists `InternalSlot[]` and derives its live workers from it, which reads like style and is not — it is the only shape that survives. The slots are now a persisted `RSBufferSlot[]` with the live list rebuilt on load. In game this would have looked like a buffer that simply ignored the network.
- New machine `gttweaks:rs_pattern_buffer_proxy` (RS Pattern Buffer Proxy, EV), the eighth and last of the parts. A buffer can only belong to one structure; the proxy is a part in a second structure that points at a buffer elsewhere and passes its multiblock's recipe questions along, so one buffer and one set of patterns can serve several machines. `RSProxyRecipeHandlerList.handleRecipe` hands the whole question to the buffer's own handler list and returns its answer rather than reimplementing it -- the rule about a recipe coming from a single slot is subtle enough that a second copy would drift. An unlinked proxy, or one whose buffer has been broken, returns the contents untouched, which reads to the multiblock as "this part supplies nothing" rather than as an error.
- The proxy holds no patterns, no ingredients and **no network node**, so `RSCapabilities` registers seven parts and not eight. That is deliberate and not an oversight: a proxy neither stores nor moves resources, and a cable laid against one should see nothing. GregTech's proxy has no grid node either. Linking earns the buffer one more internal slot (`1 + proxies`, capped at the pattern count) so each multiblock served has somewhere of its own; unlinking drops the last slot and returns its contents to the network rather than losing them with it.
- Verified on the test server 2026-09-21 (0.30.0, md5 a7839084): both parts place; linking took the buffer from 0 proxies and 1 slot to 1 proxy and 2 slots with the proxy reporting the link resolved; both survived a full server stop and start unchanged; and pushing 7 gold ingots into the proxy's slot and then breaking the proxy took the buffer back to 0 proxies and 1 slot while the chest's gold went 5 to 12, so the dropped slot was refunded exactly. 0 `ERROR` lines after startup, no `removed entries`, no gttweaks frame. The `Set<BlockPos>` of proxies persists where the `List<RSBufferSlot>` did not, which fits the array-versus-list finding above rather than contradicting it -- these elements are codec-backed positions, not `INBTSerializable`.
- `/gttweaks rspart <pos> link <x> <y> <z>` reaches the same `setBuffer` a data stick would, since GregTech's linking needs a player. The command's part lookup now also accepts the proxy, which is not an `RSNetworkPart` by design and was previously answered with "no Refined Storage part at ...".
- Unverified for the proxy, as for the buffer: no real pattern and no multiblock, so the delegation in `handleRecipe` has never actually run.
- **Confirmed in a client 2026-09-21** (0.30.0, md5 149d6093), by the user from an ATM10(3) client against the test server: a processing pattern of `4 iron ingot -> 1 netherite ingot` was encoded at a Pattern Grid and loaded into the buffer, the part reported `patterns held: 1`, and requesting one netherite ingot from a Crafting Grid put exactly 4 iron ingots into buffer slot 0. The task then sat unfinished with nothing to complete it, which is the expected outcome with no multiblock attached, and was cancelled from an autocrafting monitor. A later restart showed the part still reporting `patterns held: 1` with the 4 iron ingots in slot 0, so the pattern inventory persists as well as the slots. That closes the two largest unknowns at once: Refined Storage publishes our patterns (it believed it could make netherite because of one) and the sink's `accept` delivers, into the right slot in the right amount.
- **Proven 2026-09-21** (0.30.0, md5 98feaf22): a GregTech multiblock runs from a buffer slot, and the slots really are distinct. An Implosion Compressor was built from `setblock` (3x3x3 `gtceu:solid_machine_casing`, EV muffler, **auto maintenance hatch**, EV energy input hatch fed by a `gtceu:creative_energy` in front of it) with the RS Pattern Buffer as its item input and the RS Output Bus as its item output. Recipe `4x gtceu:flint_dust + 1x gtceu:industrial_tnt -> 3x minecraft:flint + 1x gtceu:dark_ash_dust`, 30 EU/t LV, 20 ticks. One recipe pushed into slot 0 ran and emptied it, chest flint 9 → 12. The same recipe **split across two slots** (4 dust in slot 0, 1 ITNT in slot 1) **did not run** — flint stayed 12 and both slots kept their contents, which is precisely the pooling this part exists to prevent. Completing slot 0 with its own ITNT ran it immediately, flint 12 → 15, with **slot 1's ITNT untouched**. Products travelled the whole way back through the RS Output Bus into the network. 0 `ERROR` lines after startup, no `removed entries`, no gttweaks frame.
- That closes the chain: autocrafting request, pattern published, ingredients delivered to a slot, multiblock runs from that slot, products returned to the network — every link now has evidence.
- Three defects came out of it, none of which the compiler could have caught. **The buffer must notify its aggregate handlers on a slot change**, because a multiblock subscribes its recipe logic through `RecipeHandlerList.subscribe` and that subscription is driven by the handlers' listeners; without it a buffer sits on good ingredients while the controller never looks again. **Matching must use the inner ingredient, never the `SizedIngredient`**, whose `test` checks the stack's count as well as its identity — the stack being tested is a bare count-of-one built from the resource, so the sized form passed every ingredient needing exactly one and failed every ingredient needing more, which is a multiblock that runs single-item recipes and silently refuses the rest. And **`maintenanceProblems: 0` means every problem is present, not none** (`NO_PROBLEMS` is 63, `hasMaintenanceProblems()` is `< 63`), so a fresh maintenance hatch blocks the machine; an auto maintenance hatch is what a rig should use. The third cost the most time, because a plain `gtceu:ev_input_bus` failed identically and that looked like proof the buffer was innocent when both were being blocked upstream.
- Two traps recorded alongside them: `data merge block` into a machine's inventory does not fire the change notification, so items placed that way will not wake a multiblock; and a headless server gives no reason for an idle controller, where the controller's own UI names it at once.
- `/gttweaks recipematch recipe <id>` prints one recipe in full — every item and fluid in and out, with its cost. GregTech generates most recipes at runtime so they are in no jar to read, and "what touches this item" is the wrong question when the recipe is known and its exact counts are what is wanted.
- All eight parts now carry their own texture files at `assets/gttweaks/textures/block/overlay/rs/<machine name>.png`, with `RSMachines.overlay(...)` pointing each model at its own instead of at `gtceu:block/overlay/appeng/...`. They are **placeholders** — each is a copy of the GregTech AE2 overlay for the part it mirrors, so an RS part still looks like an ME part — and RS-styled art is to come from LavaSurf. Copying rather than referencing is the whole value: replacing one becomes dropping a new PNG on the same path, with no code or registration change. The stocking variants have their own copies for that reason although they are byte-identical to the input ones today. The pattern buffer and its proxy are animated, 16-frame 16x256 strips with `.png.mcmeta` at `frametime` 4 and 6 and interpolation on, so a replacement for either must keep the strip shape or ship its own `.mcmeta` or it will render as one squashed frame. These PNGs are GregTech's artwork in a repository otherwise All Rights Reserved, which is fine for a private placeholder and should not outlive the replacement.
- New `/gttweaks rspart <pos> pattern <slot>`, which takes an encoded pattern from the player's main hand. It exists because the pattern inventory has **no UI**: right-clicking a buffer shows the bus base class's own inventory, not the 27 pattern slots, so without it there was no way to get a pattern into the part at all — the check above was impossible to run rather than merely unverified. A testing stand-in, not the widget. The stack is copied rather than consumed, an empty hand clears the slot, and anything that is not a valid encoded pattern is refused by `PatternProviderItem.isValid`.
- `RSBufferSlot` keeps amounts as `long` and keys by Refined Storage's own `ItemResource`/`FluidResource` rather than by `ItemStack` with a count-ignoring hash strategy as GregTech does — the resource is already a countless identity carrying components, and is what `accept` hands over, so nothing is converted on the way in. The narrowing to `int` happens once, at the edge where a recipe ingredient is matched and GregTech's own API leaves no choice, and it saturates rather than wrapping. A simulated match writes nothing, for the same reason the stocking parts needed: the recipe logic runs a simulated pass before every real one, and a slot that consumed during simulation would empty itself against recipes that never ran.

- The input bus, the input hatch and both stocking parts now have a **configuration screen**, `RSConfigWidget`, in place of the bus base class's own. Until now the only way to tell a part what to stock was `/gttweaks rspart <pos> config`, so the parts worked and were unusable in play; one widget serves all four, which is why it was worth doing after them rather than between them. It is GregTech's `AEConfigWidget` re-expressed over `ResourceAmount`, deliberately down to the controls -- a grid of pairs eight to a row, the standing order on top and the stock underneath; left-click with something on the cursor to configure a slot from it, right-click to clear it, left-click an empty hand on a configured slot for the amount editor (which accepts expressions like `64*9`, being GregTech's own parser), scroll to step the amount with ctrl doubling or halving it, and left-click the lower cell to take a stack of what the part is holding. Ingredients dragged from a recipe viewer land in the slot under the cursor or in the first empty one; on a fluid hatch the fluid inside a dragged or held container is what gets configured, so a water bucket asks for 1000 mB. A part also now says whether it has joined a network at all, which nothing short of a command could tell you before.
- **Nothing the widget does is applied on the client.** Each gesture sends one of five synced actions -- `rs_config_set`, `rs_config_clear`, `rs_config_amount`, `rs_stock_pickup`, `rs_config_set_ghost` -- which `RSConfigActions` applies to the real slot on the server, and the result comes back through `RSConfigSyncHandler`. That is not caution for its own sake: a slot's configuration is the part's saved data and its stock is written by the network sync, neither of which exists on a client, so there is nothing to draw but what the server sent.
- `RSConfigActions` re-checks on the server everything the widget refuses, since a client can be made to send anything, and **a stocking part refuses both the amount change and the stock pickup** there as well as in the widget. That one is an item-duplication hole rather than a tidiness rule: a stocking slot's stock is a reading of what the network holds, not material the part carries, so handing it to a player would create items from nothing and leave the network's own copy untouched. GregTech guards this in its widget and not in its action.
- Three things are shared rather than rewritten. GregTech's `AEGuiHelper` supplies the amount and selection overlays and the formatting and parsing of amounts -- none of those methods touches AE2, they take longs and coordinates, and sharing them is what keeps a configured 64,000 reading the same on an RS part as on an ME one. Refined Storage's `ResourceRendering`, fetched per resource class from `RefinedStorageClientApi`, draws every icon and builds every tooltip, which makes this widget *simpler* than GregTech's: an item, a fluid and any resource type another mod registers all go through one call, where GregTech branches on `isFluid` and unwraps an `AEItemKey` by hand. And `ResourceCodecs.AMOUNT_STREAM_OPTIONAL_CODEC` puts a slot on the wire, so a configured item keeps its data components across the network exactly as it keeps them across a save.

- A broken input bus or hatch no longer loses what the network would not take back. It hands its stock over as before, and whatever is refused -- because the network is full, or because the part was not connected to one -- now rides on the dropped machine item in a `gttweaks:rs_held_stock` data component and goes back into the slots when the part is placed. Dropping it into the world was never the answer: a slot's amount is a `long` and a part can legitimately hold hundreds of thousands of items, which as entities would be a far worse problem than the loss.
- **The ordering is the whole of it, and it is the difference between a fix and a duplication bug.** GregTech builds the drops before it removes the block -- `MetaMachineBlock.getDrops` calls `modifyDrops` and then `saveToItem` on each dropped machine item, while the flush in `onMachineDestroyed` runs later still from `onRemove`. So the flush was always too late to affect what the item carried, and writing the stock onto the item without moving the flush would have handed the player a copy of everything the network was about to be given. `modifyDrops` is therefore overridden to flush there, which leaves `collectImplicitComponents` looking at exactly the remainder the network refused. Flushing there is harmless if anything ever calls `getDrops` without breaking the block -- the slots empty into the network and the next sync pulls the same amount back -- and the later flush is then a second attempt on slots holding only what was already refused in the same tick.
- **Stocking parts are excluded**, the same item-safety rule as everywhere else in these parts: a stocking slot's stock is a reading of what the network holds rather than material the part carries, so writing it onto the item would hand the player a second copy of items the network still has.
- Only the stock travels, never the configuration, and that is what makes the restored stock safe rather than surprising: a placed part holding something it is not configured for sees it as excess and pushes it into the network on its first sync. If that network is full too it keeps holding it and tries again, as before. Carrying the configuration as well is a separate decision; GregTech copies configuration with a data stick instead.
